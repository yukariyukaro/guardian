# 戒网瘾机构公共监督平台 PRD

**文档版本：** v1.0  
**产品定位：** 面向公众的戒网瘾机构风险信息与证据索引平台  
**核心原则：** 保护受害者、坚持可核验事实、避免二次伤害、所有公开内容人工终审

## 当前边界与阅读入口

本文保留产品与内容政策；阶段安排和历史工程建议不代表能力已实现或当前任务授权。技术栈、目录、组件与运行命令直接查代码/配置；API 路径、DTO 和错误以 [OpenAPI](../contracts/openapi.yaml) 为唯一事实源，历史 API 示例不定义当前接口。阶段计划见 [plans/](../plans/全栈项目开发计划.md)，交付规范见 [响应式](响应式与页面结构规范.md)、[测试](测试与质量规范.md)和 [API 设计](API设计规范.md)。

- Guardian 是可审计、更正、撤回的公共监督平台；Archive 是首个模块，不是最终平台边界。Forum、Resources、Tools 等未来模块先完成独立产品/安全评审，显式声明路由、API namespace、权限、能力与默认关闭开关，并隔离业务数据、搜索、缓存、审核和审计，不提前显示可用入口或复用 Archive 业务 store；保留 `/institutions*`、`/sources*` 兼容。
- P0 不做真实受害者投稿、普通用户账号、公开评论/点赞/转发/私信、文件上传、AI 自动发布或危机自动回复。更正、回应和隐私举报文字只进入私有处理队列；Mock/UI 预览不冒充真实受理。
- 当前所有公开内容须经事实核查、隐私审核、法律/安全检查与人工 Publisher 终审；双人复核或已批准延迟二次自审不可省略。未来低风险自动化仅是待独立批准的规划，不能用模型置信度或路线图绕过终审。
- 前端代码与独立公开契约可公开，后端、运维和内容工作材料私有；本地目录不证明仓库可见性，未验证前按私有处理。代码许可证不自动授权数据、新闻、图片或设计素材再发布。
- 开发/设计/测试只用完全虚构数据。外部模型不得接收生产、敏感、真实投稿及其脱敏/摘要/转录派生物，也不得接收内部审核笔记、身份、私有 URL、密钥或原始材料；删除标识、关闭训练/留存不构成例外。本文 §10.3 的旧脱敏建议不构成外发许可。
- 不承诺绝对匿名、保密、实时响应或救援；发现身份泄露或现实危险交授权人工优先隐藏、清缓存并核验，AI 不擅自决定重大指控的删除/保留，不自动报警或联系机构。隐私、安全及人工终审对所有层生效，冲突时维持更严格状态并交人工决定。

## 1. 产品概述

### 1.1 一句话定位

建立一个以公开证据为基础的独立信息平台，整理存在重大争议、监管处罚、司法记录或媒体曝光的戒网瘾机构，为潜在受害者、家长、媒体和公益组织提供可核查的信息入口。

### 1.2 产品名称建议

不建议正式使用“黑名单”作为法律意义上的产品名称，因为“黑名单”容易被理解为未经审判的定罪或绝对结论。

建议使用：

- **风险机构名录**
- **戒网瘾机构公共档案**
- **青少年矫治机构风险地图**
- **机构证据档案库**
- **问题机构公开资料库**

用户界面可以出现“黑名单”作为搜索关键词兼容词，例如：

> 戒网瘾学校黑名单 / 风险机构名录

但页面正式标题应使用“风险机构名录”或“公共档案”。

### 1.3 产品目标

1. 让公众能快速查到某个戒网瘾机构是否存在公开风险记录。
2. 将分散在新闻、判决书、监管通告、视频和调查报道中的信息集中整理。
3. 为媒体、律师、公益组织和受害者提供可信的证据索引。
4. 为未来的受害者投稿和安全求助建立基础设施。
5. 在不暴露受害者身份的前提下，形成长期、可维护的公共档案。

### 1.4 非目标

第一阶段不做：

- 公开点名未经核验的个人。
- 发布受害者真实姓名、联系方式、住址、身份证、病历或聊天记录原件。
- 允许用户直接上传任意文件并自动公开。
- 让 AI 自动判断某机构“有罪”。
- 替代警方、法院、媒体或专业律师作出法律结论。
- 组织线下冲突、骚扰、围堵或报复行为。
- 发布未经核实的“爆料墙”。
- 在首页放置未经审核的匿名指控。

## 2. 用户与使用场景

### 2.1 主要用户

| 用户             | 主要需求                                         |
| ---------------- | ------------------------------------------------ |
| 潜在受害者及家属 | 了解某机构是否有公开风险记录，避免误入高风险机构 |
| 已受害者         | 查找公开报道、法律资料和安全投稿渠道             |
| 媒体记者         | 快速检索机构名称、历史事件和原始来源             |
| 律师与公益组织   | 建立案件背景资料和证据索引                       |
| 普通公众         | 了解机构运营模式和监管风险                       |
| 平台运营者       | 审核、整理、更新和撤回公开内容                   |

### 2.2 核心用户旅程

#### 场景 A：家长准备送孩子去某机构

1. 用户搜索机构名称。
2. 看到机构风险等级、所在地区、别名。
3. 查看相关报道、视频、司法文书或监管记录。
4. 判断信息来源时间和可信度。
5. 通过官方渠道或专业人士进一步核实。

#### 场景 B：记者调查某机构

1. 按地区、机构名或风险类型筛选。
2. 查看机构档案和事件时间线。
3. 下载或打开来源链接。
4. 查看平台对证据来源的整理说明。
5. 通过媒体合作渠道联系运营者。

#### 场景 C：受害者想提供线索

1. 了解平台的投稿规则和风险提示。
2. 查看平台是否承诺匿名，以及匿名边界。
3. 使用安全投稿渠道。
4. 获得匿名工单号。
5. 后续通过工单号查看人工回复。

第一阶段暂不开放场景 C 的完整功能，只保留“安全投稿说明”和“联系方式/渠道说明”页面。

## 3. 产品原则

### 3.1 事实优先，而不是情绪优先

公开内容必须能够回答：

- 发生了什么？
- 何时发生？
- 由谁报道或记录？
- 原始来源在哪里？
- 哪些内容已经确认？
- 哪些内容仍属于指控或待核实信息？

### 3.2 记录风险，不替法院定罪

页面中应明确区分：

- 官方处罚
- 法院判决
- 监管通报
- 多家媒体报道
- 单一媒体报道
- 当事人陈述
- 尚未核实的线索

不要使用没有证据支撑的表述，例如：

- “这是一家犯罪学校”
- “负责人一定虐待学生”
- “所有工作人员都是骗子”

建议使用：

- “该机构曾被某地监管部门处罚”
- “多家媒体曾报道该机构存在……争议”
- “以下内容为公开报道中的当事人陈述，平台尚未独立确认”
- “截至某日期，未找到公开回应/判决信息”

### 3.3 受害者安全高于内容完整性

任何能识别受害者的信息都不应公开，包括：

- 姓名、网名、手机号、微信号
- 精确住址和学校
- 身份证件、病历、诊断信息
- 未打码的聊天截图
- 未处理的照片和视频
- 文件中的作者名、设备名、地理位置、EXIF 信息
- 能够通过少量信息重新识别个人的组合信息

### 3.4 所有公开发布必须人工终审

AI 可以帮助：

- 摘要新闻
- 提取时间线
- 检测疑似个人信息
- 标记证据缺口
- 检查重复内容
- 生成初稿

AI 不可以直接：

- 发布机构档案
- 判定某人违法犯罪
- 自动公开用户投稿
- 自动回复受害者
- 自动决定删除或保留重大指控

# 5. 第一阶段 MVP

## 5.1 MVP 产品定位

第一版只做：

> **一个安全、可核查、以公开资料为主的戒网瘾机构风险档案库。**

不在第一版收集大量受害者隐私，不做开放式爆料社区，不做自动化 AI 审核。

这样可以同时满足：

- 快速上线；
- 降低运营者和受害者风险；
- 验证公众是否真正需要这个产品；
- 在积累审核经验后再开放投稿；
- 避免第一天就变成无法控制的内容平台。

## 5.2 MVP 功能清单

### A. 首页

首页包含：

1. 产品说明。
2. 搜索框。
3. 风险机构名录入口。
4. 最新更新的机构档案。
5. 最新整理的新闻、视频和公开文件。
6. 数据截止时间。
7. 重要免责声明。
8. 安全投稿说明。
9. 更正与回应入口。

首页不要放：

- 情绪化口号作为唯一主视觉；
- 未核验的爆料；
- 受害者故事全文；
- 容易引发网暴的个人照片；
- “曝光榜”“最恶劣机构排行”等娱乐化设计。

### B. 风险机构名录

支持：

- 机构名称搜索；
- 别名搜索；
- 地区筛选；
- 风险类型筛选；
- 资料更新时间排序；
- 证据等级筛选；
- 机构状态筛选。

建议筛选项：

- 暴力或体罚争议
- 非法限制人身自由争议
- 医疗或用药争议
- 非法收费或退费纠纷
- 监管处罚
- 司法案件
- 多家媒体报道
- 机构更名或迁址
- 已关闭/停止运营
- 尚无公开回应

搜索结果卡片显示：

- 机构名称；
- 所在省市或大致地区；
- 别名；
- 主要风险标签；
- 证据等级；
- 最近一次审核时间；
- 相关来源数量；
- “查看档案”按钮。

### C. 机构档案详情页

每个机构建立一个公开档案。

建议结构：

#### 1. 基本信息

- 正式名称；
- 曾用名和别名；
- 所在地区；
- 公开可确认的运营状态；
- 公开资料中的成立或运营时间；
- 最后更新日期。

不建议默认展示：

- 负责人个人家庭住址；
- 工作人员个人联系方式；
- 受害者所在学校；
- 机构内部未公开的精确位置；
- 可用于线下骚扰的个人信息。

#### 2. 风险概览

用谨慎措辞描述：

- 风险类型；
- 公开来源数量；
- 主要事件年份；
- 是否存在官方处罚或司法记录；
- 是否有公开回应；
- 当前资料完整度。

建议不要使用单一的“危险分数”决定一切。可以使用“证据状态”：

| 状态         | 含义                           |
| ------------ | ------------------------------ |
| 官方记录     | 有政府、法院或监管机关公开文件 |
| 多源报道     | 有多个相互独立的可靠来源       |
| 单一可靠来源 | 有一个较可信的公开来源         |
| 当事人陈述   | 主要来自个人陈述，尚未独立确认 |
| 待核实       | 已收到线索，但暂不公开具体指控 |

#### 3. 事件时间线

按日期展示：

- 事件日期；
- 事件简述；
- 来源；
- 证据状态；
- 是否有机构回应；
- 平台最后核验时间。

#### 4. 来源列表

每条来源包含：

- 标题；
- 媒体或发布机构；
- 原始链接；
- 发布日期；
- 平台收录日期；
- 来源类型；
- 关键内容摘要；
- 是否包含当事人陈述；
- 是否存在后续更正；
- 是否有存档链接。

第一版原则上只保留链接、标题和摘要，不大量转载原文或视频，降低版权和二次传播风险。

#### 5. 机构回应

如果机构存在公开声明、律师函、媒体回应或官方说明，应单独展示：

- 回应日期；
- 回应来源；
- 回应摘要；
- 平台是否能独立核验；
- 与其他公开资料之间的差异。

不允许删除回应来制造单方面叙事。

#### 6. 更正和补充入口

页面提供：

- 提交更正；
- 提交机构回应；
- 补充公开来源；
- 报告链接失效；
- 报告隐私泄露。

### D. 新闻与视频链接库

这是第一阶段最轻量、最适合率先落地的功能。

每条内容建议包括：

- 标题；
- 类型：新闻、视频、监管通告、判决书、调查报告；
- 来源名称；
- 原始链接；
- 发布时间；
- 涉及机构；
- 涉及地区；
- 标签；
- 30～100 字中立摘要；
- 证据状态；
- 最后检查日期。

视频内容建议：

- 默认只保存外部视频链接；
- 不下载、不重新托管视频；
- 不截取可能暴露受害者身份的画面；
- 不在标题中使用煽动性描述；
- 如果平台视频下方存在网暴或隐私泄露，不直接引导用户评论。

### E. 资料更正和回应

所有公开机构档案都必须有明显的：

> 提交更正 / 提交回应 / 举报隐私泄露

入口。

第一阶段可以使用简单表单，但表单内容先进入运营者邮箱或私有后台，不直接显示。

建议承诺：

- 普通内容更正：收到后 7 个工作日内处理；
- 个人信息或安全风险：优先处理；
- 紧急隐私泄露：尽快隐藏相关内容，再进行核验；
- 所有处理结果记录在内部审核日志中。

### F. 管理后台

第一阶段后台可以采用轻量的 Git/Markdown 管理方式，不急于开发复杂 CMS。

内容状态：

```text
草稿
待事实核查
待隐私审核
待法律风险审核
待发布
已发布
需修订
暂缓公开
已撤下
```

后台必须具备：

- 内容编辑；
- 来源管理；
- 标签管理；
- 变更记录；
- 发布前检查清单；
- 版本回滚；
- 操作人员权限；
- 内容撤回；
- 更正记录；
- 机构回应记录。

# 6. 内容与证据标准

## 6.1 来源等级

建议建立来源等级，而不是简单使用“真/假”。

### A 级：官方或原始材料

包括：

- 法院判决、裁定或公开司法文书；
- 政府部门公告；
- 监管处罚决定；
- 正式调查报告；
- 当事机构的公开声明；
- 原始采访或完整视频。

### B 级：多个独立可靠媒体来源

要求：

- 来源之间相互独立；
- 不是简单转载同一篇稿件；
- 具有明确时间、地点和采访对象；
- 有记者、编辑或媒体主体信息。

### C 级：单一可靠媒体或公开个人陈述

可以记录，但必须明确说明：

- 这是单一来源；
- 平台尚未独立确认；
- 不应当作已被官方认定的事实。

### D 级：匿名线索或无法核实材料

不公开具体机构指控，只进入内部待核实队列。

## 6.2 公开内容最低要求

一条机构档案至少应包含：

- 机构名称或足以定位的公开名称；
- 至少一个可访问来源；
- 来源日期；
- 事件发生时间或时间范围；
- 中立摘要；
- 证据状态；
- 最后审核日期；
- 更正或回应入口。

严重指控公开前必须由人工核验以下任一来源条件，并完成隐私、法律/安全审核与 Publisher 终审；来源条件不替代最终发布门禁。未满足条件时只进入私有待核实队列，不公开具体指控：

1. 官方记录；
2. 经核验的一手原始材料；
3. 两条以上相互独立的可靠来源；
4. 经人工核验、相互独立且可公开引用的多名陈述。

## 6.3 内容写作规范

### 推荐表达

- “公开资料显示……”
- “某媒体于某年某月报道……”
- “根据某部门公开通告……”
- “该说法来自当事人陈述，平台尚未独立确认……”
- “截至最后核验日期，未发现该机构公开回应……”

### 禁止表达

- “百分之百是骗子”
- “肯定违法”
- “所有学生都遭到虐待”
- “大家去攻击这家机构”
- “负责人全家都应该受到惩罚”
- “转发就是正义，不要核实”

# 7. 投稿系统规划

投稿系统不建议放入第一版核心发布流程，建议分阶段建设。

## 7.1 P1：安全线索提交

第一版投稿只支持：

- 文字描述；
- 机构名称；
- 事件大致时间；
- 是否愿意被联系；
- 是否允许匿名引用；
- 是否存在即时人身安全风险；
- 是否拥有公开来源。

暂不支持上传文件。

原因：

- 文件可能包含 EXIF 和作者信息；
- Word/PDF 可能包含用户名、电脑路径和修订记录；
- 图片和视频容易暴露其他受害者；
- 恶意文件可能用于钓鱼和入侵；
- 运营者需要具备独立的恶意文件处理能力。

## 7.2 P2：匿名工单

每个投稿生成：

- 随机工单号；
- 随机访问口令；
- 投稿时间；
- 当前状态；
- 审核回复；
- 补充材料入口。

不要求用户注册真实姓名、手机号或社交账号。

重要提示：

> 平台不能向用户承诺绝对匿名，只能说明已经采取哪些技术和运营措施降低识别风险。

## 7.3 投稿状态

```text
已收到
等待初步筛选
需要补充信息
进入事实核查
进入隐私审核
进入人工终审
暂不公开
已转介专业机构
已公开
已关闭
```

## 7.4 投稿安全提示

提交前明确告知：

- 不要上传身份证、病历、未打码聊天截图；
- 不要提供受害者真实姓名；
- 不要使用工作单位或学校邮箱；
- 不要在文件名中写真实姓名；
- 不要上传原始照片和视频；
- 不要发送会暴露设备信息的文件；
- 如有即时危险，应优先联系当地紧急服务、可信成年人、律师或公益组织；
- 平台不是紧急救援机构，不保证实时响应。

# 8. 审核工作流

## 8.1 公开资料录入流程

```text
发现来源
  ↓
记录原始链接与日期
  ↓
建立机构或事件草稿
  ↓
事实核查
  ↓
隐私脱敏
  ↓
法律风险检查
  ↓
人工终审
  ↓
发布
  ↓
定期复核
```

## 8.2 发布前检查清单

每一条档案发布前必须确认：

### 事实

- [ ] 机构名称没有混淆同名机构；
- [ ] 事件时间和报道时间已区分；
- [ ] 摘要没有超出来源本身；
- [ ] 来源链接可以打开或已有存档；
- [ ] 没有把个人指控写成官方认定；
- [ ] 没有隐去对事实有影响的机构回应。

### 隐私

- [ ] 没有受害者姓名；
- [ ] 没有联系方式；
- [ ] 没有身份证、病历或精确住址；
- [ ] 图片、视频和文档已检查元数据；
- [ ] 没有未成年人可识别信息；
- [ ] 没有通过多个细节组合识别个人的风险。

### 法律与安全

- [ ] 没有煽动骚扰或报复；
- [ ] 没有未经证实的犯罪定性；
- [ ] 有清晰的来源说明；
- [ ] 有更正和回应入口；
- [ ] 记录了审核人和审核日期；
- [ ] 已评估是否需要先咨询律师或合作媒体。

## 8.3 删除与撤回原则

以下情况应优先暂时隐藏：

- 发现受害者个人信息；
- 来源被证明伪造；
- 机构名称识别错误；
- 内容可能导致现实人身危险；
- 收到有明确证据支持的严重更正；
- 法院或主管机关要求处理；
- 发现平台内容被用于骚扰、围堵或报复。

“撤回”不等于删除全部内部记录。内部应保留：

- 原始来源；
- 修改前版本；
- 撤回原因；
- 审核时间；
- 操作人员；
- 后续处理决定。

# 9. 技术方案

> **架构优先级说明（v1.1）：** 本项目从第一天按全栈 API 架构建设；有效 ADR 保留在 [全栈项目开发计划](../plans/全栈项目开发计划.md) §16，API 形状只以 [OpenAPI 3.1](../contracts/openapi.yaml) 为准，交付规则见 [API 设计规范](API设计规范.md)。下方 v1.0 中“静态站点优先”的建议已废止，仅保留为历史决策记录，不得作为新代码的实现依据。

## 9.1 P0 当前架构：全栈 API 驱动

第一阶段即建立公开 API、私有审核后台和数据库隔离。前端不内置机构档案，公开页面只消费经过发布投影映射的 API 响应。

推荐：

```text
React + Vite 公共前端
    ↓ HTTPS / JSON（OpenAPI 3.1）
Fastify 模块化单体 API
    ↓                     ↓
公开投影 API          私有审核/审计 API
    ↓                     ↓
公众访问             PostgreSQL 私有网络
```

产品/模块边界及有效 ADR 见 [全栈项目开发计划](../plans/全栈项目开发计划.md)，API 路径、契约版本及公开 DTO 只以 [OpenAPI](../contracts/openapi.yaml) 为准；权限与状态交付门禁见 [API 设计规范](API设计规范.md)。公开内容仍可在私有内容仓库中维护，但必须通过后端发布流程进入 `public_content`，不能绕过审核直接构建为公共页面。

实现约束：

- 公共端、审核后台和后期投稿渠道共享 API 契约，但使用不同的响应投影和权限分区；
- 公开 API 只返回 `PUBLISHED` 内容，禁止直接序列化数据库实体；
- 所有公开内容保留人工终审闸门；P0 不开放任意文件上传；
- 后端采用 Fastify 模块化单体，PostgreSQL + Drizzle migrations；
- `web_form | direct_api | email | github_issue` 等投稿渠道只能写入私有 `submissions` 队列，不能直接修改 `public_content`；
- AI 只能提供机器辅助信号，L2/L3 内容必须人工处理，自动化策略默认关闭并 fail closed。

## 9.2 历史决策：静态站点优先（已废止）

v1.0 曾建议使用“私有内容仓库 → 静态站点构建 → CDN”的方案，以减少早期攻击面。该建议不再适用于当前实现，因为发布、撤回、更正、审计和权限边界需要由后端状态驱动。历史内容仓库仍可作为内部编辑材料来源，但不能替代 API、审核工作流或公开投影。

## 9.3 P1 后端架构

开放投稿后，再增加：

```text
Cloudflare
    ↓
Web/API 服务
    ↓
投稿接收队列
    ↓
PostgreSQL 私有网络
    ↓
审核后台
    ↓
人工发布
```

要求：

- PostgreSQL 不暴露公网；
- 管理后台只允许 Tailscale 或其他私有网络访问；
- 投稿和公开内容分离存储；
- 投稿数据与公开数据使用不同数据库角色；
- 敏感列加密；
- 备份使用 age 加密；
- 解密私钥不放在服务器；
- 日志不记录投稿正文、令牌和敏感参数；
- 所有管理操作记录审计日志。

## 9.3 P0 技术安全要求

- 强制 HTTPS；
- Cloudflare Tunnel，不开放源站入站端口；
- SSH 仅通过 Tailscale；
- 管理员启用 2FA；
- GitHub 仓库启用 2FA；
- 使用独立 GitHub 账号和 SSH 密钥；
- Git commit 使用 noreply 邮箱；
- 检查仓库历史中的个人路径、用户名和邮箱；
- 禁止将 `.env`、私钥、备份和投稿内容提交到 Git；
- 定期测试备份恢复；
- 设置内容回滚方案；
- 使用安全响应头；
- 记录必要的异常日志，但不保留不必要的身份信息。

# 10. AI 功能规划

## 10.1 AI 适合做什么

第一阶段可以在本地或私有环境中使用 AI 做：

- 新闻摘要初稿；
- 事件时间线提取；
- 来源重复检测；
- 疑似个人信息识别；
- 机构别名归并；
- 事实与观点分离；
- 审核清单辅助生成；
- 链接内容变化提醒；
- 帮助审核员发现前后矛盾。

## 10.2 AI 不得做什么

- 自动将“爆料”变成公开文章；
- 自动判断某机构违法；
- 自动给机构打危险分；
- 自动回答危机求助；
- 自动向被举报机构发送邮件；
- 自动决定是否删除内容；
- 自动保留完整受害者原文；
- 将敏感原文直接发送给外部模型 API。

## 10.3 AI 数据处理原则

文本发送给外部 LLM API 前：

1. 删除姓名、手机号、微信号、邮箱；
2. 删除精确住址、学校和单位；
3. 删除身份证、病历、案件编号等敏感字段；
4. 删除文件元数据；
5. 用内部匿名编号替代真实身份；
6. 只发送完成当前任务所需的最小文本；
7. 不向模型提供完整原始证据，除非经过严格脱敏；
8. 关闭不必要的训练和数据保留选项；
9. AI 输出必须标记为“机器辅助草稿”。

# 11. 隐私与匿名安全设计

## 11.1 运营者身份隔离

- 新项目使用独立 GitHub 账号；
- 使用新的用户名、头像和简介；
- 不复用旧项目文案和写作习惯；
- 使用独立浏览器 Profile；
- 使用独立 SSH 密钥；
- Git 使用 noreply 邮箱；
- 不把个人邮箱配置到项目仓库；
- 不将真实路径、截图、设备名上传到公开仓库；
- 不把匿名账号与个人社交账号互相关注；
- 不使用个人账号自动转发匿名邮箱；
- 运营邮件使用本地客户端分别登录，不做自动转发；
- 避免在公开内容中出现规律性个人化表达。

## 11.2 受害者数据最小化

第一阶段建议：

- 不存 IP；
- 不要求真实姓名；
- 不要求手机号；
- 不要求注册账号；
- 不收集精确定位；
- 不开放原始文件上传；
- 不保存不必要的访问日志；
- 不把投稿内容发送给不相关人员；
- 不在公开页面显示内部工单号；
- 使用随机化内部编号。

## 11.3 数据分类

| 数据等级     | 示例                     | 处理方式             |
| ------------ | ------------------------ | -------------------- |
| 公开数据     | 新闻链接、法院公开文书   | 可公开展示，记录来源 |
| 内部工作数据 | 审核笔记、来源核验记录   | 私有仓库或后台访问   |
| 敏感数据     | 投稿正文、受害者经历     | 加密、最小权限       |
| 高敏感数据   | 身份证明、病历、原始照片 | 原则上不收集         |
| 危险数据     | 可导致现实定位的信息     | 禁止存储或立即删除   |

# 12. 法律与伦理风险控制

## 12.1 诽谤和名誉风险

每个档案页面应包含：

- 信息来源；
- 来源发布日期；
- 平台整理日期；
- 事实与陈述的区分；
- 机构回应；
- 更正入口；
- 内容不是法律裁判的声明。

严重指控公开前，应考虑由专业律师、媒体或公益组织协助复核。

## 12.2 版权风险

第一阶段：

- 以外链为主；
- 只写短摘要；
- 不整篇转载新闻；
- 不下载和重新托管完整视频；
- 不使用未经授权的媒体图片；
- 对公共文件保留原始出处；
- 记录链接失效情况；
- 必要时保留经过法律评估的证据存档。

## 12.3 未成年人保护

严格禁止公开：

- 未成年人姓名；
- 学校和班级；
- 面部清晰照片；
- 可识别的聊天记录；
- 可推断家庭住址的信息；
- 与受害事件无关的家庭成员信息。

## 12.4 机构回应权

平台不需要接受机构提出的所有删除要求，但应提供：

- 事实更正渠道；
- 公开回应渠道；
- 来源异议说明；
- 争议处理记录。

对合理、更具体、有证据支持的异议，应主动复核，而不是只保留原有叙事。

# 15. 衡量指标

## 15.1 公共价值指标

- 已完成核验的机构档案数量；
- 有至少一个可靠来源的档案比例；
- 每个档案平均来源数量；
- 资料更新及时率；
- 用户通过搜索找到目标机构的成功率；
- 媒体、律师和公益组织引用数量；
- 更正请求处理时长。

## 15.2 安全指标

优先关注负面指标：

- 受害者隐私泄露次数；
- 错误指认次数；
- 未经审核内容公开次数；
- 机构名称混淆次数；
- 恶意投稿和钓鱼事件；
- 管理账号异常登录次数；
- 未完成的敏感数据删除请求数量。

## 15.3 不建议追求的指标

不要把以下指标作为主要成功标准：

- 浏览量越高越好；
- 转发量越高越好；
- 评论越激烈越好；
- 曝光对象越多越好；
- 负面标题点击率越高越好。

对于这个项目，“少发布一条无法证明的指控”有时比“多获得一万次点击”更重要。

# 16. 最先开发的具体清单

建议按以下顺序实施：

## 第一步：建立数据格式和内容政策

先完成：

- 机构档案字段；
- 来源字段；
- 证据等级；
- 风险标签；
- 发布前审核清单；
- 隐私脱敏规范；
- 更正和回应政策。

## 第二步：用静态站点做公开资料库

先不开发复杂后端，完成：

- 首页；
- 机构列表；
- 机构详情；
- 新闻/视频链接列表；
- 搜索；
- 标签筛选；
- 来源详情；
- 更正入口；
- 隐私和编辑政策页面。

## 第三步：录入第一批高质量资料

不要一开始追求数量。

优先选择：

- 有官方处罚或司法文件的机构；
- 有多家可靠媒体报道的机构；
- 来源仍能访问的机构；
- 事件脉络相对清楚的机构；
- 不需要公开受害者身份即可说明问题的机构。

## 第四步：上线前做安全审计

重点检查：

- Git 历史；
- HTML 和图片元数据；
- 服务器日志；
- 访问统计工具；
- DNS 和源站 IP；
- 管理员账号；
- 邮箱转发规则；
- 页面源码中的路径、用户名和邮箱；
- 备份文件；
- 外部分析脚本。

## 第五步：再决定是否开放投稿

网站上线并稳定运行一段时间后，再根据实际访问量、纠错请求和运营能力决定是否开放投稿。

# 17. 最终产品定义

第一阶段不应把它做成“爆料社区”，而应做成：

> **一个以公开来源为基础、带有证据等级、支持更正和机构回应的风险机构公共档案库。**

最适合首先落地的核心闭环是：

```text
机构名称
  ↓
风险档案
  ↓
事件时间线
  ↓
新闻 / 视频 / 文书来源
  ↓
证据等级与更新时间
  ↓
更正、回应和隐私举报入口
```

这个闭环足够轻量，可以快速上线；同时又能为之后的安全投稿、媒体协作、证据归档和 AI 辅助审核打下基础。真正的第一版成功标准不是“曝光了多少学校”，而是：

> 用户能够在不接触危险信息、不暴露受害者身份的情况下，快速找到可信的公开资料，并清楚知道哪些是事实、哪些是陈述、哪些仍然需要核实。
