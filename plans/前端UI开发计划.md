# Guardian 前端 UI 开发计划

**文档版本：** v1.1  
**项目阶段：** 平台化前端与 Archive 模块第一阶段  
**前端技术：** React + Vite + TypeScript strict  
**开发方式：** Contract-first；Mock/Real API Adapter 可切换，前后端并行开发  
**产品定位：** 可审计的风险机构公共档案，而不是曝光社区或社交平台  
**平台定位：** Archive 是第一个模块；未来 Forum、Resources、Tools 通过 module manifest 接入，数据、搜索、权限和审核边界保持隔离

> 本文保留阶段安排、设计意图和原始任务，不表示当前工程现状、已实现能力或本轮修改授权。历史目录、技术/脚本清单和 API 示例不作为第二份事实源；实际工程读取代码与配置，API 形状只读 [OpenAPI](../contracts/openapi.yaml)。现行规则集中于 [响应式规范](../docs/响应式与页面结构规范.md)、[测试与质量规范](../docs/测试与质量规范.md)和 [API 设计规范](../docs/API设计规范.md)，历史架构决策见 [全栈计划](全栈项目开发计划.md)。开发、Mock、截图与评测只用完全合成数据，历史脱敏描述不授权真实派生材料；具体指控不可因标为待核实而公开，所有公开内容仍须 Publisher 人工终审。

## 1. 本阶段目标与边界

本阶段只做 React + Vite 前端 UI，不实现后端、数据库、邮箱接入、GitHub App 或 AI agent。目标是先交付一套可以接入 OpenAPI、使用 Mock API 独立运行的前端产品：

- 面向公众的“风险机构公共档案”网站。
- 面向运营者的内容审核后台 UI。
- 可替换的 Mock 数据和 API client，不把真实机构资料编译进前端。
- 完整的加载、空数据、错误、暂时隐藏、撤回和失效来源状态。
- 移动端、键盘操作、语义 HTML、焦点可见性和对比度达标。
- 前端代码可公开开源；不包含真实投稿、真实身份、后端密钥和生产数据。

本阶段不做：

- AI 自动审查或自动发布页面。
- 邮箱/GitHub Issues 接入页面和真实集成。
- 任意文件上传、拖拽上传、图片/视频投稿组件。
- 公开评论、点赞、转发、排行榜和社交动态流。
- “危险分数”“最恶劣机构”或带有定罪含义的可视化。
- 真实数据录入；所有开发数据仅使用完全虚构内容，不使用真实材料的去标识化派生物。

后期 API、邮箱、GitHub Issues 和 AI agent 统一进入私有 `Submission` 队列；本阶段只为未来集成预留类型和路由边界，不提前展示未实现功能。

## 2. 设计方向：可审计的公共档案

### 2.1 核心概念

采用 **Archive / Dossier（档案 / 证据卷宗）** 作为视觉概念：

> 用户不是在浏览“曝光榜”，而是在查阅一份有来源、有日期、有更正机制的公共档案。

设计要让用户一眼理解：

```text
机构身份 → 证据状态 → 事件时间线 → 原始来源 → 机构回应 → 更正入口
```

### 2.2 视觉性格

- 克制、可靠、编辑部式，而不是煽动性新闻或社交媒体。
- 信息密度中等，元数据清晰，给重要内容留出呼吸空间。
- 用颜色表达状态，不表达“有罪/无罪”。
- 把来源、日期、更新时间、资料范围和限制说明放在可见位置。
- 允许局部不对称，但不能牺牲检索效率和内容安全。

### 2.3 视觉系统

**色彩角色：**

```text
paper-50       暖白阅读背景
ink-950        主要文字与标题
navy-800       顶部壳层、深色区块
blue-600       链接、主按钮、焦点环
slate-500      次要元数据与分隔线
amber-600      待核实、需要注意
red-600        隐私/安全紧急状态和危险操作
sage-600       已核验或已处理的辅助状态
```

建议以暖白、墨色和深海军蓝为主，蓝色只用于行动和链接，琥珀色用于“待核实”，红色只用于隐私安全警告和撤回/危险操作。不要用红色给所有风险标签上色。

**字体：**

- `Noto Sans SC`：导航、标签、表单、元数据和正文 UI。
- `Noto Serif SC`：首页主标题、引用和来源摘要中的少量编辑性内容。
- `IBM Plex Mono`：证据编号、请求编号、日期代码和技术状态。
- 字体自托管或随前端构建，避免第三方字体请求泄露访问信息。

**布局：**

- 桌面最大内容宽度 1200～1280px。
- 桌面使用 12 列网格；详情页采用“主内容 + 证据侧栏”结构。
- 移动端改为单列，筛选器变为底部抽屉或全屏面板。
- 卡片使用细边框、轻微纸张层次和小圆角，不使用堆叠玻璃拟态。
- 重要信息通过章节标题、状态图例、时间线和来源行表达，不靠大量装饰。

### 2.4 动效原则

- 首屏只做一次有节奏的标题、搜索框和信任信息渐入。
- 列表筛选使用 150～220ms 的淡入/位移动画。
- 时间线节点可按顺序出现，但不能让用户等待才能阅读。
- 卡片 hover 只改变边框、阴影和来源链接状态，不做夸张缩放。
- 所有动画支持 `prefers-reduced-motion: reduce`。
- 不使用自动轮播、滚动劫持、强制视差或让敏感提示短暂闪烁的动效。

### 2.5 平台模块边界

Archive 是当前唯一实现的公共模块，负责机构档案、事件、来源、回应和更正入口。未来 Forum、Resources、Tools 等模块不得通过复制 Archive 页面或共享不受约束的全局状态接入，而应注册显式的 module manifest：

```ts
type ModuleManifest = {
  id: "archive" | "forum" | "resources" | "tools";
  publicRoutes: string[];
  adminRoutes: string[];
  navigation: { label: string; href: string; order: number }[];
  capabilities: string[];
  apiNamespace: string;
};
```

模块必须拥有独立的 feature、ViewModel、API adapter、权限声明和审核边界；平台 Shell 只负责导航、主题、错误边界和运行时配置，不直接读取模块业务数据。Archive 的 `/institutions*`、`/sources*` 路由作为长期兼容入口保留，新模块不得复用这些路径。

## 3. 参考研究如何转化为 UI

本次使用 Tavily 对公共档案、调查时间线和安全投稿体验做了定向检索。参考模式来自：

- [ICIJ Offshore Leaks Database](https://offshoreleaks.icij.org/)：面向实体的搜索、筛选、数据范围、限制说明、关联关系和逐条报告错误。
- [DocumentCloud](https://www.documentcloud.org/)：来源库、出版者/日期元数据、原始来源和文档上下文。
- [SecureDrop](https://securedrop.org/)：安全提示先于投稿动作、明确说明匿名边界和下一步。
- [ProPublica](https://www.propublica.org/)：公共利益编辑部语气、调查内容分组和公开更正入口。
- [The Guardian corrections](https://www.theguardian.com/info/complaints-and-corrections)：把更正、回应、投诉和复核路径分开，并提供持续可访问的更正记录。
- [National Security Archive chronology](https://nsarchive.gwu.edu/news/foia/2022-01-06/capitol-riot-chronology)：事件时间、证据描述、来源链接和图例。
- [Trusting News corrections toolkit](https://trustingnews.org/trustkits/corrections)：更正、澄清、撤回的语义区分和公开更正日志。

转化原则：

- 搜索要支持正式名称、别名、地区和证据状态。
- 时间线每个节点都要能回到来源，不能只做图形化叙述。
- 每条记录显示数据范围、最后审核时间、来源限制和“报告错误”入口。
- 更正、机构回应、隐私举报是三个不同操作，不做一个模糊的“反馈”按钮。
- 安全投稿页面先讲风险和平台边界，再显示表单。

| `/corrections/new`    | 提交更正或机构回应 | 安全提示、文本表单、成功引用号             |
| `/privacy-report`     | 报告隐私泄露       | 高优先级警告、最小字段、快速提交           |

### 4.2 管理端 UI 路由

第一阶段只做后台壳和核心内容审核界面，不接真实身份服务：

| 路由                               | 页面目标                                 |

| `/admin/sources`                   | 管理来源、证据等级和链接状态             |

## 5. 关键页面设计规格

### 5.1 首页 `/`

**首屏：**

- 左上角产品名和“公共档案”副标题。
- 中央/偏左的编辑性标题，例如“从公开记录开始，理解机构风险”。
- 一句短说明：平台整理公开来源，不替法院作出结论。
- 一个主搜索框，支持机构名、别名、地区；搜索按钮始终明显。
- 次级入口：“浏览机构名录”“查看来源库”。
- 首屏底部放数据更新时间、资料范围和方法说明入口。

**首屏之后：**

1. 信任条：已公开档案、来源数量、最近更新日期；不使用夸张 KPI。
2. 最近更新档案：3～5 条，显示证据状态、地区、来源数和人工复核日期。
3. 来源流：新闻、视频、判决、通告、调查报告，用紧凑行而非营销卡片。
4. “如何阅读档案”：四步横向节奏——身份、事件、来源、回应。
5. 方法与限制：数据范围、证据等级、内容不是法律判决的说明。
6. 安全行动区：提交更正、报告隐私问题、阅读安全说明。

**禁止：**曝光排行榜、最恶劣机构、热点评论、情绪化受害者照片、未核验爆料墙。

### 5.2 机构名录 `/institutions`

采用“搜索头 + 筛选轨 + 结果列表”的研究型界面：

- 顶部保留搜索词和搜索范围说明。
- 桌面端左侧为筛选轨：地区、风险标签、证据状态、运营状态、更新时间。
- 结果区同时支持紧凑列表和更宽松卡片两种密度，但首版优先列表，便于比较来源和日期。
- 每个结果显示：机构名、已核验别名、近似地区、风险标签、证据状态、来源数量、最近人工审核时间。
- 结果页的搜索、筛选、排序和分页全部同步 URL，可复制和刷新。
- 移动端筛选器变为底部抽屉，打开后有“应用筛选”和“清除”按钮。
- 结果为空时解释“没有匹配公开档案”而不是暗示机构不存在风险。

必须设计的状态：初始、加载骨架、结果、无结果、网络错误重试、内容暂时不可见、撤回记录不可公开。

### 5.3 机构详情 `/institutions/:slug`

页面采用“档案封面 + 证据正文 + 来源侧栏”的节奏：

1. **身份头部：** 正式名称、别名、近似地区、运营状态、最后审核时间。
2. **身份核验提示：** 同名机构识别提示，强调需结合地区、别名和来源核对。
3. **证据状态图例：** 官方记录、多源报道、单一可靠来源、当事人陈述、待核实；每项有文字说明，不能只用颜色。
4. **风险摘要：** 风险类别、主要事件年份、公开来源数、是否有机构回应；不显示单一危险分数。
5. **事件时间线：** 日期/日期范围、事件摘要、证据状态、来源入口、机构回应状态、平台复核日期；增加类型图例和可筛选能力。
6. **来源集合：** 每条显示标题、出版者、来源类型、发布时间、证据等级、链接状态、短摘要。
7. **机构回应：** 独立区域，标明回应日期、来源和平台能否独立核验。
8. **程序行动栏：** 提交更正、提交机构回应、补充公开来源、报告失效链接、报告隐私问题。
9. **数据限制页脚：** 资料覆盖范围、最后更新日期、平台非司法机构声明。

对于暂时隐藏、撤回、来源失效或待核实状态，必须提供解释型状态组件，不显示空白页。

### 5.4 来源库与来源详情 `/sources`

来源库使用“研究台账”风格：

- 以来源行为主，不使用大图封面墙。
- 筛选：来源类型、机构、地区、证据等级、发布时间、链接状态。
- 来源行：标题、出版者、类型、日期、关联机构/事件、30～100 字中立摘要、证据状态、最后检查日期。
- 以外链打开原始来源，显式标注“离开本站”。
- 视频只保留外部链接，不做视频下载、重托管和自动截图。

来源详情要回答：

- 这是什么来源？
- 谁发布的？
- 什么时候发布？
- 它能支持什么？不能支持什么？
- 关联了哪些机构和事件？
- 链接是否可用、重定向或已存档？
- 是否有后续更正？

### 5.5 更正/回应/隐私表单

表单采用“安全提示 → 选择请求类型 → 最小字段 → 确认”四步结构：

- 请求类型单选：事实更正、机构回应、补充公开来源、失效链接、隐私问题。
- 关联机构/来源可搜索，但不要求用户填写内部 ID。
- 具体描述字段有长度限制和清晰示例。
- 联系方式选填，旁边明确风险提示。
- P0 不出现上传按钮、拖拽区或“稍后添加附件”占位。
- Turnstile/反滥用位置只做 UI 占位，真实校验由后端完成。
- 成功页只展示随机请求引用号、预计处理路径和安全提醒，不展示内部数据库 ID。
- 失败页不回显用户提交的敏感正文。
- 隐私举报表单视觉优先级高于普通更正，但不使用恐慌式视觉。

### 5.6 政策页

政策页不要堆成一面长墙，使用“短摘要 + 可展开细节 + 目录锚点”：

- 编辑政策：证据等级、事实/陈述区分、人工终审、回应和更正。
- 隐私政策：公开/内部/敏感数据分级、保存期限、删除方式、日志边界。
- 安全说明：平台做什么、不做什么、不能承诺什么、不要提交什么、遇到即时危险找谁。

### 5.7 管理后台

后台使用比公共端更密集但同一品牌系统：

- 左侧窄导航 + 顶部当前角色和环境提示。
- 仪表盘以“待处理队列”优先，不做营销统计。
- 审核列表显示状态、风险等级、渠道、更新时间和负责人。
- 详情页左侧内容，右侧审核清单和状态操作。
- 发布/隐藏/撤回按钮必须显式要求理由；危险操作使用确认对话框。
- Researcher、Reviewer、Publisher、Admin 的不可用操作要解释原因，而不是静默消失。
- 审计日志默认脱敏；敏感读取显示二次确认。

每个组件都要在 UI 状态预览中展示：默认、hover、focus、disabled、loading、error、empty、mobile。组件名称按领域组织，不建立一个无法维护的“万能卡片”组件。

## 7. 前端工程结构与数据策略

项目当前没有 `package.json`、`src/`、Vite 配置或测试配置，因此从零建立。实现必须遵循 **Page → Feature ViewModel → Domain → API Adapter → Mock/Real API** 的单向边界：页面只组合 ViewModel 和领域组件；组件不直接 fetch；领域层不依赖 React；Adapter 负责将契约 DTO 转为领域模型，Mock 与真实 API 使用同一接口。

项目从零建立：


技术栈：

- Vite + React + TypeScript strict。
- React Router。
- TanStack Query 管理服务器状态。
- React Hook Form + Zod 管理表单。
- Tailwind CSS + CSS Variables。
- Radix UI 或等价的无障碍原语。
- `openapi-typescript` + `openapi-fetch` 生成类型安全 API client。
- Vitest + Testing Library。
- Playwright。
- pnpm、ESLint、Prettier。
- 建议加入 Storybook（`@storybook/react-vite`）作为组件状态画廊，不接真实 API。
- shadcn/ui 使用本地源码模式（`new-york`、Tailwind v4、CSS variables）；只引入所需 primitive，并通过 wrapper/domain 组件统一产品语义、无障碍和状态样式，不把生成代码当黑盒依赖。

状态原则：

- 机构、来源和详情数据只由 TanStack Query 管理。
- 搜索词、筛选、排序和分页写入 URL。
- 不把整套机构数据放进 Redux 或自建全局 store。
- Mock API 使用完全虚构数据，且字段形状与 OpenAPI 一致。
- API 错误只展示安全消息和必要的支持引用号，不显示堆栈、SQL、路径或身份字段。

## 8. 设计素材与图像生成计划

本项目不需要大量人物或场景图片。为了保护受害者、避免视觉煽动并保持档案气质，素材以抽象、非识别性、可替换为主。

### 8.1 生成设计参考图

在正式编码前，用 `imagegen-frontend-web` 生成 **6 张独立的横向设计参考图**，一张对应首页一个区块，不合并成长图或拼贴：

1. Hero：暖白纸面、墨蓝档案线条、搜索入口、无人物。
2. Trust/Scope：资料范围、更新时间和方法说明的编辑部版式。
3. Latest Records：机构档案与来源条目的高密度但舒展的列表节奏。
4. Timeline：来源链接和事件节点的时间线构图。
5. Safety/Corrections：更正和安全行动区，清晰而非恐慌式。
6. Closing CTA：极简的“搜索档案 / 查看方法”收束区。

统一提示词约束：

- 16:9 或 16:10 横向。
- 暖白、墨蓝、冷蓝、琥珀色的同一品牌世界。
- 不出现真实人物、受害者、学校、机构名称、身份证明或可识别地点。
- 不生成可读的真实新闻标题或法律文本。
- 设计图用于构图参考，生产 UI 文案由 React 渲染，不依赖生成图里的文字。

### 8.2 可选生产素材

只生成以下非识别性素材：

- 纸张、扫描边缘、档案标签、低对比网格。
- 抽象的地区线条或资料关系线，但不对应真实地图坐标。
- 来源卡片所需的无文字纹理或单色封面。
- 深色安全说明区的低对比噪点纹理。

大部分视觉效果优先使用 CSS、SVG 和设计 token，避免引入大体积位图。图片输出统一转为 WebP/AVIF，设置明确的 `alt` 和懒加载；装饰性图片使用空 `alt`。

### 8.3 不使用的素材

- 受害者照片、模糊人脸、制服、真实校舍和可定位街景。
- 带有真实机构名称的生成截图。
- 用红色警报、血腥画面或惊悚缩略图制造点击。
- 任何让机构看起来已经被法律定罪的视觉符号。

## 11. 前端验收标准

### 视觉

- [ ] 首页不是通用 SaaS 模板，而是具有档案/编辑部识别度的公共产品。
- [ ] 首屏搜索是最清晰的主任务。
- [ ] 页面在列表、详情、来源和政策之间保持同一色彩/字体/边框语言。
- [ ] 没有紫蓝渐变、玻璃拟态堆叠、虚假 KPI 或无意义发光。
- [ ] 颜色表达状态，不让用户误读为司法结论。
- [ ] 图片和纹理不包含人物、真实名称、真实地点或可识别受害者。

### 交互

- [ ] 搜索支持正式名称和已核验别名。
- [ ] 筛选、分页、排序可以通过 URL 分享和刷新恢复。
- [ ] 时间线节点可以查看来源，且有文本替代。
- [ ] 外链离站、失效、重定向、存档和不可用状态清楚可见。
- [ ] 更正、机构回应和隐私举报是不同入口。
- [ ] 表单成功只显示随机引用号，不显示内部数据库 ID。
- [ ] P0 不存在文件上传控件。

### 无障碍与响应式

- [ ] 键盘可以完成导航、搜索、筛选、弹层和表单。
- [ ] 焦点可见，焦点顺序合理，弹层关闭后焦点回到触发控件。
- [ ] 所有字段有 label、错误提示和状态说明。
- [ ] 不依赖颜色单独表达证据状态或风险状态。
- [ ] 390px 宽度下核心任务不需要横向滚动。
- [ ] `prefers-reduced-motion` 下没有强制动效。

### 安全与工程

- [ ] Mock 数据全部完全虚构，不导入真实材料及去标识化派生物。
- [ ] 前端不包含 API 密钥、数据库连接串、OIDC secret、私有服务器地址或真实投稿。
- [ ] 前端不相信客户端传入的 `visibility`、风险等级或审核结果。
- [ ] 公开页面只渲染发布投影形状。
- [ ] API 错误不显示堆栈、SQL、内部路径和身份字段。
- [ ] 构建产物和截图中没有真实邮箱、个人路径和敏感文字。

## 12. 执行结论

先按以下顺序开始：

```text
平台模块边界与项目级规范
  ↓
Design tokens + shadcn wrappers + 设计参考
  ↓
OpenAPI 契约、生成类型、Mock/Real Adapter
  ↓
Vite/React 工程骨架与 Platform Shell
  ↓
Archive 首页搜索 vertical slice
  ↓
机构名录与机构详情
  ↓
来源库与政策页
  ↓
更正/回应/隐私举报表单
  ↓
管理后台 UI
  ↓
响应式、无障碍、性能和隐私 QA
```

本阶段最重要的判断标准不是页面数量，而是用户能否安全、快速、准确地完成：

> 搜索一个机构 → 理解证据状态 → 查看事件与来源 → 看到机构回应 → 知道如何更正或报告隐私问题。

后期的直接 API、邮箱、GitHub Issues 和 AI 功能必须作为独立的私有投稿工作台接入，不能为了“先做 UI”而在公共端提前出现自动发布、文件上传或未经核实的公开内容。
