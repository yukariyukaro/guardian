**文档版本：** v1.0  
**基于 PRD：** [产品 PRD](../docs/戒网瘾机构公共监督平台-PRD.md)

**代码开放策略：** 前端开源；后端、部署配置、敏感数据与运营工具私有

## 0. 执行摘要

### 0.1 第一版要交付什么

第一版不是静态资料页，也不是开放式爆料社区，而是一个真正由后端驱动的公共档案平台：

1. 公众通过 React 前端访问机构名录、搜索、机构档案、事件时间线和来源链接。
2. 所有公开内容由后端 API 提供，前端不内置机构数据。
3. 运营者通过受保护的审核后台创建、编辑、核验、发布和撤回内容。
4. 任何公开内容都必须经过人工终审。
5. 公众可以提交更正、机构回应或隐私泄露报告，但第一版不接收任意文件，也不允许投稿自动公开。
6. 前端代码、组件、页面和 API 类型契约开源；后端源代码、部署文件、数据库、审核记录和敏感配置私有。

### 0.2 开发顺序

```text
项目边界与安全规则
        ↓
公开 API 契约与数据模型
        ↓
前端/后端工程骨架与 CI
        ↓
公开机构名录和搜索
        ↓
机构详情、来源和时间线
        ↓
审核后台与发布工作流
        ↓
更正、回应和隐私举报
        ↓
安全审计、部署、种子数据和上线
        ↓
安全投稿与匿名工单（后续版本）
```

### 0.3 第一版明确不做

- 不做公开评论、点赞、转发排行或社区私信。
- 不做用户注册和普通用户账号体系。
- 不做任意文件上传。
- 不收集身份证、病历、原始照片、原始视频或聊天记录。
- 不让 AI 自动发布、自动定罪、自动回复危机求助。
- 不公开受害者姓名、联系方式、学校、精确住址或可重新识别信息。
- 不开发“危险分数”或“最恶劣机构排行榜”。
- 不把机构档案写成未经证实的犯罪结论。

# 1. 产品和代码边界

## 1.1 仓库规划

建议从一开始拆为以下仓库，避免开源前端与私有后端混在一起：

| 仓库                 | 可见性  | 内容                                                     | 是否包含敏感数据                 |
| -------------------- | ------- | -------------------------------------------------------- | -------------------------------- |
| `guardian-web`       | Public  | React + Vite 前端、公开页面、审核后台 UI、前端测试       | 否                               |
| `guardian-contracts` | Public  | OpenAPI 规范、公开数据类型、错误码、契约测试样例         | 否                               |
| `guardian-api`       | Private | 后端 API、数据库迁移、后台业务规则、审核服务             | 可能包含内部逻辑，不提交真实投稿 |
| `guardian-ops`       | Private | Docker Compose、服务器配置、备份脚本、监控配置、部署文档 | 是，严禁提交密钥                 |
| `guardian-content`   | Private | 机构档案草稿、审核笔记、内部来源核验记录                 | 是                               |

如果初期维护成本过高，可以暂时将 `guardian-contracts` 放在 `guardian-web` 的 `contracts/` 目录中，但 API 契约必须独立、可版本化，不能直接从后端私有仓库临时复制。

### 1.1.1 前端开源边界

开源仓库可以包含：

- 页面、组件和样式；
- 公开 API 类型；
- Mock 数据和 Storybook 示例数据；
- 不含真实个人信息的测试数据；
- 表单校验规则；
- 前端错误码展示逻辑；
- 通用内容审核 UI 组件。

禁止包含：

- `.env`、API 私钥、数据库连接串；
- 真实投稿、审核笔记和内部联系人；
- 管理员邮箱和真实身份信息；
- 服务器地址、Tailscale 节点信息、备份密钥；
- 未脱敏的截图、图片、视频和文档；
- 任何能够反向定位运营者或受害者的路径、用户名和元数据。

## 1.2 平台模块边界与注册协议

Archive 是第一阶段上线的第一个业务模块，不等于平台的全部产品边界。未来 Forum、Resources、Tools 等模块必须通过显式 manifest 注册，不能通过复制 Archive 页面、共享业务 store 或复用不受约束的审核队列接入。

```ts
type ModuleManifest = {
  id: "archive" | "forum" | "resources" | "tools";
  displayName: string;
  publicRoutes: string[];
  adminRoutes: string[];
  apiNamespace: string;
  capabilities: string[];
  navigation: { label: string; href: string; order: number }[];
};
```

注册协议约束：

- 每个模块拥有独立的 domain、公开/管理 DTO、API namespace、权限声明、审核边界和 feature flags；
- 平台 Shell 只负责身份上下文、导航、主题、错误边界、运行时配置和 module manifest 加载，不直接读取模块业务数据；
- 搜索、缓存、审计和发布策略按模块隔离，跨模块查询必须经过显式的只读聚合接口；
- Archive 的 `/institutions*`、`/sources*` 路由长期保留兼容，新增模块不得占用或隐式改写这些路由；
- 前端使用 Page → Feature ViewModel → Domain → API Adapter → Mock/Real API 分层，后端使用 module → application → domain → infrastructure 分层；
- 模块注册不能放宽人工终审、公开投影、隐私最小化或投稿隔离规则。

## 1.3 运行时边界

```text
浏览器
  │
  │ HTTPS / JSON API
  ▼
React + Vite 前端（公开仓库）
  │
  ├── 公开 API：任何人可读，严格返回公开投影
  └── 管理 API：仅管理员、审核员可访问
              │
              ▼
        私有后端 API（私有仓库）
              │
       ┌──────┴──────┐
       ▼             ▼
  PostgreSQL       审核/审计服务
  私有网络         私有网络
```

前端构建产物可以放在 CDN 或静态资源服务上，但这不代表项目是静态站点：

- 页面结构由 React 运行时渲染；
- 机构、来源和事件数据通过 API 动态获取；
- 内容发布、撤回和更正都由后端状态驱动；
- 浏览器不保存完整内容数据库；
- 管理操作必须经过后端权限和审核规则。

# 2. 技术选型与工程约束

## 2.1 前端技术栈（确定）

| 类别       | 选型                                  | 用途                         |
| ---------- | ------------------------------------- | ---------------------------- |
| 构建       | Vite                                  | 开发服务器、构建和环境管理   |
| UI         | React + TypeScript                    | 页面和组件                   |
| 路由       | React Router                          | 公共页面和后台路由           |
| 服务端状态 | TanStack Query                        | API 请求、缓存、重试和失效   |
| 表单       | React Hook Form + Zod                 | 管理表单和客户端校验         |
| 样式       | Tailwind CSS + CSS Variables          | 响应式布局和主题             |
| 无障碍组件 | Radix UI 或等价无障碍组件             | 对话框、菜单、标签页、提示等 |
| API 类型   | openapi-typescript + openapi-fetch    | 从公开契约生成类型安全客户端 |
| 测试       | Vitest + Testing Library              | 单元测试和组件测试           |
| E2E        | Playwright                            | 关键用户流程和回归测试       |
| 包管理     | pnpm                                  | 锁定依赖、工作区和脚本       |
| 代码质量   | ESLint + Prettier + TypeScript strict | 统一质量门槛                 |

### 2.1.1 前端状态原则

- 服务器数据统一由 TanStack Query 管理。
- 不把机构档案复制到 Redux 或全局状态中。
- 仅在确实需要时使用轻量 UI 状态，例如筛选面板是否展开、当前主题或未提交表单状态。
- URL 保存可分享的搜索条件、分页和筛选项。
- 任何需要权限的页面都不能只依赖前端路由守卫，最终权限必须由后端判定。

## 2.2 后端技术栈（确定）

| 类别      | 选型                                      | 用途                           |
| --------- | ----------------------------------------- | ------------------------------ |
| 运行时    | Node.js + TypeScript                      | API 和后台服务                 |
| HTTP 框架 | Fastify                                   | REST API、插件和高性能请求处理 |
| 校验      | Zod 或 TypeBox                            | 请求/响应校验                  |
| API 文档  | OpenAPI 3.1                               | 前后端共享契约                 |
| 数据库    | PostgreSQL                                | 公开档案、审核状态和审计记录   |
| ORM/迁移  | Drizzle ORM                               | 类型安全查询和迁移             |
| 认证      | OIDC + Cloudflare Access 或等价私有身份层 | 管理后台身份认证               |
| 缓存/队列 | 第一版不引入；后续按需加入 Redis/BullMQ   | 异步审核、链接检查和通知       |
| 文件存储  | 第一版禁用上传；后续使用隔离对象存储      | 脱敏后材料存储                 |
| 日志      | 结构化 JSON 日志                          | 错误、性能和安全审计           |
| 部署      | Docker Compose + 私有 VPS                 | API、数据库和监控              |

> 后端实施细节以[API 设计规范](../docs/API设计规范.md)为准：Fastify 模块化单体；本地推荐 WSL2 Linux 文件系统与 Docker Compose，Windows 原生 Node 也可用于无数据库的虚构开发模式。Node Inspector 只绑定 loopback，迁移采用 expand-and-contract，不在 API 启动时自动执行。框架实现可以替换，但不能改变已发布的公开 API 契约和安全边界；变更必须先更新契约、迁移说明和兼容性测试。

## 2.3 基础设施

- 公共前端：Cloudflare Pages、对象存储 CDN 或等价托管。
- API：私有 VPS 上的 Docker 容器，通过 Cloudflare Tunnel 对外提供 HTTPS。
- 管理后台：管理路由和管理 API 通过 Cloudflare Access、Tailscale 或等价私有网络限制访问。
- PostgreSQL：仅允许 Docker 私有网络访问，不暴露公网端口。
- SSH：仅通过 Tailscale 或其他零信任内网访问。
- DNS：只暴露代理/CDN 地址，不暴露源站 IP。
- 监控：最小化错误监控，不上传投稿正文、表单字段和个人信息。

# 3. 角色、权限与内容状态

## 3.1 角色

| 角色       | 权限                                       |
| ---------- | ------------------------------------------ |
| Public     | 浏览公开档案、搜索、提交更正/回应/隐私举报 |
| Researcher | 创建草稿、录入来源、编辑未发布内容         |
| Reviewer   | 事实核查、隐私审核、退回修改               |
| Publisher  | 发布、撤回和处理高风险变更                 |
| Admin      | 账号、权限、系统设置和审计日志             |

原则：

- `Researcher` 不能直接发布内容。
- `Reviewer` 可以批准事实和隐私检查，但高风险内容仍需 `Publisher` 终审。
- `Publisher` 的发布动作必须写入审计日志。
- `Admin` 不应默认拥有查看全部投稿正文的权限，采用最小权限和按需授权。
- 第一版至少保留两人审核机制；如果只有一名运营者，必须采用延迟发布和二次自审流程。

## 3.2 内容状态

### 公开档案状态

```text
DRAFT                 草稿
FACT_CHECK            待事实核查
PRIVACY_REVIEW        待隐私审核
LEGAL_REVIEW          待法律风险审核
READY_TO_PUBLISH      待发布
PUBLISHED             已发布
REVISION_REQUIRED     需修订
TEMPORARILY_HIDDEN    暂时隐藏
WITHDRAWN             已撤回
```

### 更正/回应请求状态

```text
RECEIVED              已收到
TRIAGED               已初筛
NEED_MORE_INFO        需要补充
IN_REVIEW             审核中
ACCEPTED              已接受
PARTIALLY_ACCEPTED    部分接受
REJECTED              不采纳并记录理由
CLOSED                已关闭
```

状态转换必须由后端校验，前端不能自行拼接状态。高风险状态转换必须产生审计事件。

## 4.4 P3：受控 AI 自动化

| 编号    | 功能               | 说明                                              |
| ------- | ------------------ | ------------------------------------------------- |
| AI-003  | AI 审核工作台      | 展示摘要、字段抽取、证据缺口、来源冲突和 PII 高亮 |
| AI-004  | 低风险规则门禁     | 仅允许 L0 白名单字段进入受控自动发布              |
| AI-005  | 来源关联与冲突检测 | 关联机构、来源和重复投稿，低置信度进入人工队列    |
| AI-006  | 审核质量分析       | 统计误报、漏报、人工覆盖率和自动发布撤回率        |
| OPS-001 | 自动发布熔断       | 支持按全局、渠道和内容类型暂停自动发布            |
| OPS-002 | 自动发布抽样复核   | 对低风险自动发布内容进行人工抽样和回滚演练        |

AI 只能提供信号或在服务端规则引擎明确允许的 L0 范围内触发发布；不能自动发布涉及暴力、虐待、医疗、未成年人、受害者陈述、危机或个人信息的内容。

## 4.5 P4：高级材料处理

- 受控文件上传、隔离扫描、元数据清理和过期删除。
- OCR、音视频转录和隐私检测等多模态能力。
- 更细粒度的媒体、律师和公益组织工作区。
- 地区地图、统计视图、订阅和数据导出。

P2 及以后功能都必须在 P0/P1 的审核、隐私和审计机制稳定后再做；P3 的自动化功能必须先完成离线评测、人工抽样和一键暂停机制。

## 6.3 统一多渠道投稿模型

所有后期贡献入口都必须先进入私有 `submissions` 区域，不能直接写入 `public_content`。统一模型使网页表单、直接 API、邮箱和 GitHub Issues 使用同一套权限、审核、保存期限和审计规则。

```text
web_form | direct_api | email | github_issue
        ↓
intake adapter
        ↓
normalize / deduplicate / PII screening
        ↓
AI triage（如启用）
        ↓
human review OR bounded auto-publish gate
        ↓
Publisher/manual publication
        ↓
public_content
```

`submission` 的关键字段：

| 字段                        | 说明                                              |
| --------------------------- | ------------------------------------------------- |
| `channel`                   | `web_form`、`direct_api`、`email`、`github_issue` |
| `external_id`               | 外部系统事件 ID；不能单独作为公开 ID              |
| `source_metadata`           | 渠道来源、schema 版本和受限来源信息               |
| `normalized_content`        | 规范化后的最小文本或结构化内容                    |
| `restricted_raw_reference`  | 加密原始材料引用，不直接返回给前端                |
| `schema_version`            | 渠道输入版本                                      |
| `idempotency_key`           | 防重复提交和重放                                  |
| `risk_level`                | `L0`～`L3` 风险等级                               |
| `risk_flags`                | PII、危机、未成年人、恶意链接等信号               |
| `consent_and_contact_state` | 是否允许联系、匿名引用和后续沟通                  |
| `ai_review_status`          | 未运行、已完成、失败、需人工接管                  |
| `human_decision`            | 人工审核最终决定                                  |
| `retention_deadline`        | 到期删除或复核日期                                |
| `created_at` / `updated_at` | 生命周期时间戳                                    |

投稿状态：

```text
RECEIVED
  → NORMALIZED
  → DEDUPLICATED
  → AI_TRIAGED
  → HUMAN_REVIEW
  → PRIVACY_REVIEW
  → PUBLISHER_APPROVAL
  → PUBLISHED
```

允许的异常和终止状态：

```text
NEED_MORE_INFO
QUARANTINED
REJECTED
WITHDRAWN
EXPIRED
```

低风险自动化分支：

```text
AUTO_PUBLISH_ELIGIBLE
  → RULE_GATE
  → PUBLISHED
```

状态转换必须由后端校验。前端不能通过传入 `risk_level=low`、`visibility=published` 或伪造审核结果绕过规则。

### 风险分级与发布策略

- **L0：低风险结构化内容。** 公开来源链接、来源元数据、链接失效报告和非敏感标签修正。只有在 schema 校验、重复检测、URL 检查和 PII 检查全部通过，并命中白名单字段时，才允许受控自动发布；必须保留抽样复核和完整审计。
- **L1：一般公开资料补充。** AI 可以生成结构化草稿和摘要，但默认进入 Reviewer 队列；不能因为 AI 置信度高就跳过事实核查。
- **L2：涉及机构违法、虐待、暴力、医疗、未成年人或受害者陈述。** 必须人工事实核查、隐私审核和 Publisher 终审。
- **L3：危机、威胁、个人信息、原始材料、疑似恶意文件或自伤风险。** 隔离并优先人工处理，禁止自动回复、自动发布、自动联系机构或自动把原文发送给外部模型。

`publish_low_risk` 不是 AI 的自由工具，而是后端规则引擎的受限动作，只能作用于 L0 白名单字段；任何不确定性、服务异常或校验失败都必须 fail closed。

### 渠道适配器职责

每个适配器只负责：认证或验签、解析、规范化、去重、保留受限来源引用和写入统一队列。适配器不能直接发布内容。

- **直接 API：** 校验 schema、`Idempotency-Key`、配额、请求签名或服务身份。
- **邮箱：** 校验 Webhook/IMAP 身份，提取纯文本，隔离 HTML、链接、邮件头和附件。
- **GitHub Issues：** 校验 GitHub App 签名、允许的组织/仓库/标签，处理 Issue、评论、编辑和删除事件。

### AI agent 边界

邮箱正文、GitHub Issue、评论、Markdown、链接、附件和模型输出都按不可信输入处理。AI agent 不能执行投稿内的指令，不能把投稿文本当系统提示，不能访问任意数据库、网络、密钥或管理接口。

允许的工具白名单：

```text
normalize_text
detect_pii
suggest_redactions
extract_institutions_dates_sources
find_duplicate_submissions
classify_risk
create_review_draft
check_public_url
```

默认禁止：发送邮件、评论或 Issue；修改或删除公开内容；联系机构或外部组织；任意数据库查询；任意网络下载；直接发布高风险内容。

统一记录每次 AI 运行的模型和版本、执行时间、脱敏输入版本、输出、风险信号、人工最终决定和失败原因。AI 输出必须标记为“机器辅助”。

# 7. API 契约计划

## 7.1 契约优先协作流程

每个跨层功能以 vertical slice 交付，顺序固定为：

```text
Issue / acceptance criteria
  → OpenAPI schema + examples + error cases
  → contract lint / breaking-change check
  → frontend generated types + Mock handler + ViewModel
  → backend route + validation + public projection
  → contract/integration/E2E tests
  → human privacy and content-safety review
```

Definition of Ready：范围、公开/私有数据边界、权限、错误码、加载/空/错误/隐藏状态、隐私风险和验收用例已明确。Definition of Done：契约已版本化、Mock 与真实 API 共用 DTO 形状、前后端测试通过、公开投影字段回归通过、无敏感数据进入日志/截图/fixtures、移动端和无障碍状态已覆盖。

前后端并行约束：

- 契约和示例由契约负责人维护，前后端不得各自复制 DTO；
- 前端不等待真实服务才开始，使用 Mock/Real Adapter 切换；
- 后端不以数据库实体直接驱动前端，必须实现公开 DTO 映射；
- 任何 breaking change 先更新契约版本和兼容期，再改实现；
- 子代理只修改分配范围，跨边界变更通过共享契约和交接记录完成；
- 合并前必须运行契约 lint、类型检查、测试、构建和隐私回归。

## 7.2 契约原则

1. `guardian-contracts` 中的 OpenAPI 3.1 是公开 API 的唯一事实来源。
2. 每次 API 变更先改契约，再改后端和前端。
3. 破坏性变更必须升级 `/api/v1` 版本或提供兼容期。
4. 公开响应对象与管理响应对象严格分离。
5. 所有写入接口都必须定义限流、错误码和审计要求。
6. API 文档不得暴露内部数据库表名、服务器地址和敏感流程。

```text

GET  /api/v1/admin/submissions

POST /api/v1/admin/submissions/{id}/triage
POST /api/v1/admin/submissions/{id}/request-info
POST /api/v1/admin/submissions/{id}/approve
POST /api/v1/admin/submissions/{id}/reject
POST /api/v1/admin/submissions/{id}/publish-low-risk
POST /api/v1/admin/submissions/{id}/quarantine
```

`publish-low-risk` 只能在服务端规则引擎确认 L0 白名单条件后执行。前端不能通过请求体传入低风险等级或公开状态绕过规则；所有自动发布必须有幂等键、审计记录、抽样复核和全局暂停开关。

管理接口必须同时经过：

- 审计日志记录；
- 敏感读取告警或二次确认。

## 7.6 标准错误响应

```json
{
  "error": {
    "code": "VALIDATION_ERROR",

```

前端只展示安全的 `message`，不展示堆栈、SQL 错误、内部路径和身份信息。

# 9. Post-MVP 开发计划

后期功能必须按“统一投稿内核 → 渠道适配器 → AI 预审 → 受控自动化”的顺序建设。任何渠道都不能绕过私有 `submissions`、隐私审核、事实核查和审计。

## 9.1 Post-MVP 1：统一投稿内核与直接 API（第 13～16 周）

前提：P0 已稳定运行，运营者已经有真实审核能力、应急流程和可恢复备份。

功能：

- `Submission` 表、渠道适配器接口和统一状态机。
- 无账号文字投稿和随机工单号。
- `POST /api/v1/intake/submissions` 直接贡献 API。
- 文字和结构化公开资料提交，不接受文件。
- `Idempotency-Key`、限流、配额、请求大小限制和重复检测。
- 受信任 partner API 的 OAuth client credentials、mTLS 或 HMAC 认证设计。
- 管理端统一多渠道投稿队列。
- 投稿和公开档案严格分离。
- 记录来源渠道、schema 版本、外部 ID、保存期限和联系同意状态。

验收：

- API 内容落库后只进入私有投稿队列，不能直接出现在公开搜索。
- 重复请求不会重复创建投稿。
- 低权限客户端不能写入机构、来源或公开内容表。
- 可以通过随机引用查看工单状态，但不能推断内部 ID。

不能做：

- 投稿自动公开高风险内容。
- 使用浏览器可见的特权 API Key。
- 自动承诺匿名、保密、救援或实时响应。
- 将完整投稿直接发送给外部 LLM。

## 9.2 Post-MVP 2：邮箱接入与 AI 预审（第 17～20 周）

邮件流转：

```text
专用收件箱/入站邮件服务
  → Webhook 签名或 IMAP 认证
  → 邮件解析与规范化
  → HTML/链接/附件隔离
  → PII、恶意内容和 Prompt Injection 检测
  → 私有 Submission 队列
  → AI agent 预审
  → 风险分级
  → 人工审核或 L0 规则门禁
```

功能：

- 使用独立收件地址或入站邮件服务，不自动转发到真实邮箱。
- 验证供应商 Webhook 签名，或仅从私有网络使用经过认证的 IMAP。
- 优先提取纯文本；HTML、邮件头、签名、追踪链接和附件按不可信数据处理。
- 第一版邮箱接入不接受附件；后续附件必须进入隔离区、恶意文件扫描和元数据清理。
- 邮件正文进入统一投稿队列，发件地址和邮件头进入受限字段。
- AI 进行入口分类、PII 检测、脱敏建议、机构匹配、日期/来源抽取、重复检测、风险分级和安全摘要。
- AI 识别“忽略规则”“直接发布”等 Prompt Injection，并将其作为投稿内容而非系统指令。
- AI 输出默认进入 Reviewer 队列；模型不可用、输出不符合 schema 或不确定时自动转人工。
- 禁止自动向投稿者或被举报机构发邮件，禁止 AI 对危机内容作救援承诺。

AI agent 允许的工具白名单：

```text
normalize_text
detect_pii
suggest_redactions
extract_institutions_dates_sources
find_duplicate_submissions
classify_risk
create_review_draft
check_public_url
```

默认禁止：任意数据库查询、任意网络下载、发送邮件/评论/Issue、修改或删除公开内容、联系机构或外部组织、直接发布高风险内容。

## 9.3 Post-MVP 3：GitHub Issues 接入（第 21～24 周）

架构要求：

- 工程仓库 Issues 与贡献接收仓库分离。
- 使用单独的私有 intake repository，不让受害者在公开工程仓库提交敏感内容。
- 使用最小权限 GitHub App，不使用个人 PAT 作为长期生产凭据。
- 通过签名 Webhook 或受控 Poller 接收事件。
- 限制允许的组织、仓库、Issue Form 和标签。

事件流程：

```text
GitHub App Webhook
  → 签名/仓库/标签校验
  → Issue ID 和 delivery ID 去重/重放防护
  → Markdown/链接/评论/附件安全检查
  → 标准化 Submission
  → AI 预审（如启用）
  → 人工审核或 L0 规则门禁
```

功能：

- 处理 Issue 创建、编辑、评论、关闭和删除事件。
- Issue 正文、Markdown、评论、外链和附件按不可信输入处理。
- 默认不保存原始附件，只保留必要的加密受限引用。
- GitHub 用户名、邮箱、Issue URL、原文、评论和 Webhook delivery ID 不进入公开 API。
- 按 Issue ID、事件 ID 和 delivery ID 去重。
- 若未来开放公开 Issue，仅允许低敏感度更正或链接报告，并明确“不匿名、不提交受害者信息”。

## 9.4 Post-MVP 4：AI 审核工作台与受控自动上线（第 25～28 周）

AI 审核能力：

- 机构实体匹配：使用名称、别名、地区和来源上下文，低置信度进入人工确认。
- 证据字段抽取：日期、来源、事件类型、机构回应和公开链接。
- 来源一致性检查：提示摘要是否超出原始来源，但不判断法律真伪。
- 跨 API、邮箱和 GitHub Issue 的重复和关联发现。
- 识别暴力、限制自由、医疗、未成年人、隐私、危机和恶意文件信号。
- 生成机器辅助摘要、待核实问题和缺失证据清单。
- 机构公开回应对照和来源冲突提示。
- 来源失效、重定向和重大变化检测。
- 审核质量分析：precision、recall、误报、漏报、人工覆盖率和自动发布撤回率。

### 自动发布风险分级

- **L0：** 公开来源链接、来源元数据、链接失效报告和非敏感标签修正。只有 schema、重复、URL 和 PII 检查全部通过，并命中白名单字段，才允许受控自动发布。
- **L1：** 一般公开资料补充。AI 可生成结构化草稿，但默认进入 Reviewer 队列。
- **L2：** 涉及机构违法、虐待、暴力、医疗、未成年人或受害者陈述。必须人工事实核查、隐私审核和 Publisher 终审。
- **L3：** 危机、威胁、个人信息、原始材料、疑似恶意文件或自伤风险。隔离并优先人工处理，禁止自动回复、自动发布、自动联系机构或把原文发送给外部模型。

`publish_low_risk` 只能由服务端 `publication_policy` 规则引擎触发，AI 只提供信号，不得自行调用公开写入动作。自动发布必须支持：

- 白名单字段和内容类型；
- 渠道和每日配额；
- 幂等和完整审计；
- 人工抽样复核；
- 一键全局/按渠道暂停；
- 30 分钟内撤回。

默认关闭自动发布；完成完全合成 golden set 评测和人工抽样只是试运行前置条件，仍须独立评审与明确批准，不绕过现行人工终审门禁。

## 9.5 Post-MVP 5：受控材料与多模态能力（第 29 周以后）

只有在具备以下能力后才开放：

- 恶意文件隔离扫描和病毒扫描；
- EXIF、文档修订记录和设备元数据清理；
- OCR、音视频转录和隐私检测在隔离环境运行；
- 文件大小、类型、数量、下载和访问审计；
- 对象存储私有桶和过期删除；
- 材料与投稿人身份隔离；
- 运营者专用隔离设备或工作环境；
- 明确的删除、保存和紧急销毁策略。

多模态能力只能把脱敏后的派生文本或结果交给 AI，不能因此放宽人工发布门禁。

## 10.1 测试分层

| 层级         | 目标                         | 主要工具            |

| 组件测试     | 页面交互、表单和错误态       | Testing Library     |
| API 集成测试 | 数据库、权限和公开投影       | Vitest + 测试数据库 |

| E2E          | 关键真实流程                 | Playwright          |
| 安全测试     | 越权、注入、敏感数据和限流   | 专项测试脚本        |
| 手工审核     | 内容准确性、隐私和法律风险   | 审核清单            |

## 10.2 必须覆盖的 E2E 流程

1. 公众打开首页并搜索机构。
2. 公众使用别名搜索并打开详情。
3. 公众筛选证据状态和地区。
4. 公众查看事件时间线和来源链接。
5. 公众提交更正请求。
6. 管理员登录并查看审核队列。
7. Researcher 创建机构草稿。
8. Reviewer 退回内容并记录理由。
9. Publisher 完成清单后发布内容。
10. Publisher 暂时隐藏内容，公众端不再显示。
11. 无权限用户访问管理 API 被拒绝。
12. API 异常时前端展示安全错误，不泄露堆栈。

## 10.3 隐私回归测试

每次发布前自动检查：

- 响应中没有 `email`、`phone`、`ip`、`user_agent`、`internal_note` 等禁止字段。
- 页面 HTML 中没有本地绝对路径、真实邮箱和私有域名。
- 构建产物中没有 `.env`、密钥和测试投稿。
- 日志样本中没有表单正文和访问口令。
- 公开搜索无法搜到草稿、隐藏和撤回记录。

## 10.4 多渠道接入专项测试

### 直接 API

- [ ] OAuth/mTLS/HMAC 或等价认证、时间窗和签名校验。
- [ ] `Idempotency-Key` 重复请求不会重复落库。
- [ ] 超额配额、超大请求、恶意字段和错误 schema 会被拒绝。
- [ ] 公开 API 无法查询私有 Submission。
- [ ] 客户端无法伪造 `visibility=published` 或低风险等级。
- [ ] partner 只能访问被授权的 schema、字段和配额。

### 邮箱接入

- [ ] 伪造 Webhook、伪造发件人和恶意邮件头会被隔离。
- [ ] HTML 注入、钓鱼链接和 Prompt Injection 会被标记。
- [ ] 重复邮件、转发链、超长内容和异常编码可安全处理。
- [ ] 附件默认拒收或进入隔离区，不进入公共内容流程。
- [ ] AI 服务不可用、超时或输出不符合 schema 时自动转人工。
- [ ] 不会自动回复投稿人、联系机构或向真实邮箱转发。

### GitHub Issues

- [ ] Webhook 签名错误、重放和错误仓库会被拒绝。
- [ ] Issue 创建、编辑、评论、关闭和删除事件均可幂等处理。
- [ ] 恶意 Markdown、外链、评论和附件按不可信输入处理。
- [ ] Issue ID、事件 ID 和 delivery ID 可去重并防重放。
- [ ] GitHub App 只拥有必要仓库和事件权限，密钥可轮换。
- [ ] 公开 Issue 模式不会接受匿名爆料或受害者敏感信息。

### AI 与自动发布

- [ ] 使用完全合成 golden set 评测分类、PII、机构匹配和风险分级，不导入真实材料及脱敏派生物。
- [ ] 记录 precision、recall、误报、漏报、人工覆盖率和自动发布撤回率。
- [ ] AI 不可访问未授权表、调用未授权工具或生成高风险公开写入动作。
- [ ] AI 超时、模型切换、输出不符合 schema 时 fail closed。
- [ ] L2/L3 内容自动转人工，不能由 AI 直接发布。
- [ ] 自动发布默认关闭，支持全局、按渠道和按内容类型暂停。
- [ ] 自动发布内容可在 30 分钟内撤回，且撤回原因进入审计日志。

# 13. 部署与运维计划

## 13.1 环境

| 环境       | 用途          | 数据                             |
| ---------- | ------------- | -------------------------------- |
| Local      | 本地开发      | 假数据或本地测试数据库           |
| Preview    | PR 预览和 E2E | 完全虚构数据                     |
| Staging    | 发布前联调    | 完全虚构种子数据                 |
| Production | 正式服务      | 经过终审的公开内容和最小运营数据 |

禁止将生产投稿复制到本地、Preview 或 Staging。

## 13.2 发布流程

```text
开发分支
  ↓
Pull Request
  ↓
CI：类型 / Lint / 测试 / 构建 / 契约检查
  ↓
Preview 环境人工验收
  ↓
合并 main
  ↓
前端发布 + 后端镜像构建
  ↓
Staging 数据库迁移演练
  ↓
生产迁移与健康检查
  ↓
发布记录和回滚点
```

## 13.3 备份与恢复

- PostgreSQL 定期加密备份。
- 备份异地存放，解密私钥不在服务器。
- 备份不包含不必要的访问日志和临时文件。
- 每月至少一次恢复演练，MVP 上线前必须完成一次。
- 恢复演练不得把真实投稿复制到公开环境。
- 记录恢复耗时、数据完整性和失败原因。

## 13.4 应急预案

必须准备四份一页纸预案：

1. **错误内容公开：** 立即隐藏、保留内部证据、核验、修订、记录通知。
2. **隐私泄露：** 立即下线相关内容、清理缓存、检查副本和日志、通知受影响者的安全渠道。
3. **账号或密钥泄露：** 撤销会话、轮换密钥、检查审计日志、暂停高风险操作。
4. **服务器或数据库泄露：** 隔离主机、保全日志、轮换凭据、评估影响、恢复干净环境。
5. **邮箱/GitHub 接入异常：** 立即停用对应 connector、撤销 Webhook/应用凭据、暂停该渠道入队，保留必要的事件指纹并从干净状态恢复。
6. **AI 或自动发布异常：** 立即全局关闭 `publish_low_risk`、转人工队列、检查最近自动发布记录、在 30 分钟内完成错误内容撤回。

## 13.5 多渠道与 AI 运维要求

- 邮箱、GitHub App 和 AI 服务使用独立凭据、独立轮换周期和独立暂停开关。
- 邮件 Webhook、GitHub Webhook 和 AI 调用只记录请求 ID、事件 ID、模型版本和结果状态，不记录原始正文。
- 监控渠道积压、重复率、验签失败、AI 超时、schema 失败、人工覆盖率和自动发布撤回率。
- AI 供应商不可用时，投稿仍需保留在私有队列，不得丢弃或自动公开。
- 自动发布策略默认关闭；任何开启都必须记录操作者、策略版本、范围、配额和过期时间。
- 提供按全局、渠道、内容类型和 partner 维度的一键暂停机制。
- 生产邮件、Issue 和投稿绝不复制到 Local、Preview 或 Staging。

# 16. 决策记录

## ADR-001：前端开源，后端私有

**决定：** React 前端和公开 API 契约开源；后端源代码、部署配置、审核记录和敏感数据私有。  
**原因：** 方便公众审查界面和数据展示逻辑，同时保护管理流程、基础设施和受害者数据。

## ADR-002：从第一天使用全栈 API 架构

**决定：** 公共页面从后端 API 获取内容，不把机构档案编译进前端。  
**原因：** 后续需要发布、撤回、更正、审计和权限控制；静态内容方案会导致后续迁移成本和安全边界不清。

## ADR-003：第一版不接收文件

**决定：** P0 只接受更正、回应和隐私举报文字，不开放任意文件上传。  
**原因：** 文件包含元数据、恶意载荷和受害者隐私，必须先建设隔离扫描、脱敏、存储和删除能力。

## ADR-004：公共 API 使用公开投影

**决定：** 数据库实体不得直接序列化给公众，所有响应经过公开 DTO。  
**原因：** 防止草稿、内部备注、审计字段、联系方式和未来新增敏感字段意外泄露。

## ADR-005：AI 后置且只能辅助

**决定：** AI 不进入 P0 主线，不得自动发布、定罪、回复危机求助或决定删除。  
**原因：** 本项目的主要风险是错误指认、二次伤害和隐私泄露，不应以自动化换取未经验证的效率。

# 17. 计划执行原则

1. 先做数据边界和权限，再做视觉细节。
2. 先做 API 契约，再写前端请求代码。
3. 先做公开投影和状态机，再做管理表单。
4. 先做可撤回、可审计、可恢复，再扩大内容规模。
5. 任何“为了快”而跳过人工终审、隐私检查或数据库隔离的方案都不接受。
6. 每完成一个阶段都要更新本文档中的勾选项、契约版本和风险记录。
7. 只有 P0 的内容、审核和安全门槛全部满足，才进入公开上线。

> 第一版的成功不是“尽快发布更多机构”，而是建立一个可以被公众使用、被审核、被纠正、被撤回、被审计且不会轻易伤害受害者的全栈系统。
